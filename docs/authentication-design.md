# Guided account setup: design and open questions

[← Architecture](architecture.md)

This is a proposed authentication redesign, **not shipped functionality**. The current
login uses an app-specific password generated by the user on Apple's account site.

## Intended experience

One iCloud mailbox, with multiple sender aliases:

1. Start `icloud-agent auth login`.
2. Authorize the application through Apple in a browser, including any two-factor check.
3. Save the resulting credential or tokens in the native OS credential store.
4. Discover the account's available sender addresses and calendars.
5. Select entries using arrow keys to move, Space to toggle, and Enter to save.
6. Reuse the saved authorization on subsequent invocations. Let the user revisit selections.

If Apple authorization supplies tokens, generating an app-specific password may be
unnecessary. The exact credential type and refresh flow depend on Apple's integration
requirements. Account credentials should be entered into Apple's sign-in surface;
the CLI should not need to retain the main Apple Account password.

## Authentication route to investigate first

Apple documents authorization for supported third-party Mail, Calendar, and Contacts
apps. Its support article also describes email-address and alias changes appearing
after reauthorization. It does not publish a developer API contract or establish
whether arbitrary local CLIs qualify:

- [Apple: access iCloud data in third-party apps](https://support.apple.com/en-us/121539)
- [Apple Developer iCloud OAuth request endpoint](https://developer.apple.com/contact/request/icloud-oauth2/)

On September 21, 2026, the developer endpoint redirected to Apple Developer sign-in.
The form behind sign-in, enrollment eligibility, scopes, endpoints, and client-registration
requirements have not been verified. No access request has been submitted.

Before implementation, establish whether Apple supports a distributable native/public
client, a local redirect or another local authorization mechanism, credential refresh,
and Mail/CalDAV access without a deployed server or a secret embedded in the CLI.
Also verify how the authorized API returns the complete set of sendable aliases,
including custom-domain addresses. Standard IMAP folder discovery does not provide
that account-level inventory.

The documented alternative is [manual app-specific-password generation](https://support.apple.com/en-us/102654).
We have not established a supported API for automatically generating these passwords.

## Why an iCloud.com cookie is not sufficient evidence

A working iCloud web session establishes access to the web services it authorizes.
It does not, by itself, establish access to account.apple.com's app-password management
or provide an IMAP/SMTP password. These paths need separate verification.

If official authorization is unavailable, a private web integration would require a
separate feasibility investigation: fresh sign-in, two-factor challenges, trust/session
expiry, alias discovery, app-password generation, and recovery after revocation.
Request traces can contain passwords, cookies, and mailbox contents. Use an explicitly
authorized test account and sanitize fixtures before committing them. Do not build
production behavior from one successful replay or ship a user's captured cookie.

## Selections are access controls

- **Sender aliases:** selected addresses are allowed From identities for draft creation
  and sending. They share one mailbox; deselecting an alias does not hide incoming mail
  addressed to that alias. Verify availability from Apple, not from message headers or
  a user-supplied arbitrary address.
- **Calendars:** selected IDs restrict discovery and all event reads and writes. Check
  the same policy in the shared backend used by CLI and MCP, including opaque event IDs.
- **Persistence:** save selections atomically after discovery and explicit confirmation.
  Cancellation preserves existing settings. An empty selection means none; it must
  never silently mean all. Newly discovered resources stay disabled until selected.
- **Picker:** use a maintained terminal prompt library. Support keyboard operation,
  clear selected states without color, and Ctrl-C cancellation. The interactive picker
  must not appear during an agent operation or contaminate MCP/JSON stdout.

No selection policy is implemented in the current release. A future implementation
needs tests proving that disabled resources cannot be accessed through direct IDs,
raw operation calls, existing drafts, or MCP tools.
